All figures **measured**, not estimated. HTML sizes are `wc -c` on the built
`out/` file; gzip is `gzip -c <file> | wc -c`. No Lighthouse / Core Web Vitals
numbers are claimed — none were run in this environment.

- **Baseline:** `main` @ `e03427b`, `npm run build`, served at domain root.
- **v0.12:** `feat/v0.12-productization`, same build command.
- Both against the same committed snapshot (`live-feed.json`, `2026-09-03T07:59:03Z`).

## What changed

- **Progressive loading.** List pages server-render ~18 `FeedCard`s, then a
  client `<LoadMore>` appends further matching cards from `index/latest.json`
  (fetched once, on click). With JS off, the first page + section header are the
  whole section — plus a link to `/trends` for the full list.
- **One lean card.** `FeedItem` is a flat, display-only projection; the old
  `EventCard` serialised large `trendData` sub-objects (finance/sports/thread
  branches) into markup on every card.
- **No route-level Suspense shell.** Removing `app/loading.tsx` means each page's
  content is pre-rendered into `<main>` instead of a `<!--$?-->` boundary with a
  "Loading…" fallback that required JS to resolve (this affected production too).
- **`<Link prefetch={false}>` on card story links** — a 60-card list no longer
  fires 60 route prefetches on load.

## Deploy artifact size

`out/` is **170 MB** (baseline ~58 MB). The increase is 607 additional
`/story/*` pages: every in-scope cluster (763, up from 156) now has a page, so
every internal `/story/<slug>` link resolves and every story is deep-linkable.
Median story page is 69 KB HTML + a ~50 KB RSC payload. Well within GitHub Pages'
1 GB limit; upload time increases modestly. If this becomes a constraint, the
mitigation is to prune RSC `.txt` payloads or reduce the story-page shell — not
to reintroduce unlinkable stories.
